You are looking for a purpose-built educational/research OS for ML on constrained hardware, with the central assumption that CPU cycles, old storage, FPGAs, MCUs, and SBCs are cheap or already owned, while RAM/VRAM is the scarce resource. Given the state of sw-tos, demo-memory, and especially emufpga, I think there is a coherent research direction here that is more interesting than merely “Linux, but with ML syscalls.”

The central idea I would pursue is:

Treat model state as the OS's primary virtualized resource, the way conventional operating systems treat address space and pages.

I would tentatively call the research concept Model Virtual Memory (MVM), implemented first as an extension/research branch of SWTOS and later perhaps as a separate sw-mtos, sw-aios, or sw-mlos repository.

sw-tos is already unusually well positioned for this. It is a microkernel aimed at small CPUs/FPGA soft cores, needs no MMU, has provider abstractions for resident/flash/SD-backed images, block caching, reclaimable allocations, and emulator-first validation. demo-memory, meanwhile, is explicitly investigating bounded memory, eviction policies, sparse retrieval, hard budgets, adaptive scheduling, and the problem of finding “the small part of memory that matters.” And emufpga has already taken the most radical step: treating parameters as a stream rather than as randomly accessed RAM, keeping only activations, accumulators, scales, and state resident.

Those projects can converge.

1. The historical analogy

The interesting question isn't:

“What syscalls does an ML operating system need?”

It is:

“What assumptions made conventional OS architecture necessary, and what corresponding assumptions are changing for ML?”

A rough analogy looks like this:

Historical computing problem	OS/hardware response	ML equivalent
RAM smaller than programs	virtual memory	model-state virtualization
disk much larger than RAM	paging	weight/KV/context paging
locality of reference	page cache	tensor/block residency
expensive CPU	scheduling/time sharing	accelerator scheduling
slow I/O	DMA, buffering	tensor prefetch/stream pipelines
vector workloads	SIMD/vector units	tensor engines
FP workloads	FP coprocessor	ML coprocessor/NPU
independent processes	virtual address spaces	independent inference sessions
file working set	page working set	inference working set
disk prefetch	read-ahead	layer/expert prediction
swap thrashing	working-set control	KV/weight thrashing
NUMA	topology-aware allocation	RAM/VRAM/NPU/storage topology
filesystem cache	unified page cache	unified model-state cache

And there is an important distinction.

Classical VM assumes:

program accesses arbitrary virtual address
        ↓
MMU translates
        ↓
page happens to reside somewhere

ML gives the OS vastly more information:

token t
 ↓
layer 0
 ↓
layer 1
 ↓
...
 ↓
layer N

or, for MoE:

layer
 ↓
router
 ↓
experts {3, 17}

So an ML OS often knows the future access sequence.

That is enormously useful.

Traditional paging is reactive.

ML paging can be predictive.

Have the OS manage typed ML objects:

size
precision
location
next-use
reuse-frequency
recompute-cost
reload-cost
priority
mutability

Then residency becomes an OS policy problem.

For example:

                 ┌──────────────┐
                 │ FPGA BRAM    │
                 └──────▲───────┘
                        │
                 ┌──────┴───────┐
                 │ MCU SRAM     │
                 └──────▲───────┘
                        │
                 ┌──────┴───────┐

The OS decides where every ML object should live.

That becomes a semantic memory hierarchy.

3. Weight paging is different from VM paging

Your emufpga work points at the most important distinction.

Weights are usually:

immutable,
huge,
sequentially consumed,
predictable,
often reused across multiple requests.

That makes them terrible candidates for ordinary VM-style demand paging and excellent candidates for streams. Your SPM work explicitly takes this approach: weights live in cheap sequential storage and compute moves to the stream rather than requiring full parameter residency.

So MVM should probably expose at least three access classes:

STREAM
CACHE
RESIDENT

Example:

Object	Likely policy
dense layer weights	STREAM
MoE expert weights	CACHE/PREFETCH
activations	RESIDENT
recent KV	RESIDENT
old KV	CACHE
embeddings index	CACHE
RAG documents	STORAGE
LoRA adapter	CACHE
tokenizer tables	RESIDENT

That immediately produces a more useful abstraction than ordinary pages.

4. Make residency the equivalent of process priority

The kernel scheduler today asks:

Which process gets CPU time?

An ML scheduler might ask two simultaneous questions:

Which inference stream gets compute?

and

Which model state gets scarce RAM?

So scheduling becomes two-dimensional:

          COMPUTE
             ↑
             |
session A ───┼──── memory residency
session B ───┼────
session C ───┼────
             |

A request might hold:

weights: streamed
KV:      12 MiB resident
context: compressed
RAG:     evictable

Another might hold:

weights: shared
KV:      1 MiB
expert:  pinned

The scheduler then optimizes working sets, not just timeslices.

This is where your existing bounded-memory work becomes directly relevant. demo-memory already experiments with FIFO versus LRU, hard runtime budgets, adaptive scheduling, and retrieval-budget selection.

You can turn those from MLPL demonstrations into candidate OS policies.

This could be particularly educational.

    object: WEIGHT_TILE,

The kernel/provider layer can then choose:

remote node

SWTOS already has an embryo of exactly this provider concept. Its catalog/loading machinery abstracts resident, block, SPI-flash, and SD image sources behind provider operations and block reads.

Generalize:

Then:

That would be a very natural evolution of SWTOS rather than an unrelated rewrite.

6. Predictive paging becomes much more powerful

Conventional operating systems try to infer future references.

A transformer tells you quite a lot of them directly.

If currently executing:

layer 10

then fetch:

layer 11

while layer 10 computes.

So:

storage       CPU/FPGA

fetch L10 ───────►
                 compute L10
fetch L11 ───────►
                 compute L11
fetch L12 ───────►

This is basically OS-managed double buffering.

For MoE it gets more interesting:

router output
     ↓
expert 7 = 0.63
expert 19 = 0.21
expert 3 = 0.09

The OS could interpret this as a prefetch probability distribution.

That is genuinely unlike traditional paging.

An experimental algorithm:

prefetch expert 7 immediately
prefetch expert 19 if bandwidth idle
leave expert 3 on storage

Now the routing network is effectively supplying paging hints.

7. KV cache should absolutely be an OS resource

This is probably the easiest bridge to modern practical inference.

KV cache is:

dynamic,
per-session,
increasingly large with context,
partly disposable,
partly compressible,
partly shareable,
temporally structured.

vLLM now supports KV offloading from GPU to CPU and multi-tier secondary storage, promoting blocks back upward on demand.

That's useful precedent, but you can push the abstraction down into the OS.

Imagine:

kv_alloc(session, tokens)
kv_pin(recent_window)
kv_demote(old_range)
kv_compress(range)
kv_drop(range)

with tiers:

HOT       SRAM/VRAM
WARM      DRAM
COLD      SSD
ARCHIVE   regenerate/summarize/drop

Then you can experiment with:

Recency

Keep latest 2K tokens hot.

Importance

Keep tokens with high attention scores.

Summary

Replace old KV with summarized state.

Recompute

Drop cheap-to-reconstruct state.

Quantize
FP16 → Q8 → Q4

as KV gets colder.

This gives you the equivalent of:

clean page
dirty page
compressed page
swapped page

but adapted to inference.

8. Recompute should be a first-class alternative to paging

This is an area where ML differs dramatically from ordinary programs.

For a normal OS:

Lost memory must generally be restored.

For ML:

Some state can simply be recomputed.

So every object could carry:

reload_cost
recompute_cost
storage_cost

Then eviction can choose:

STORE
DISCARD + RECOMPUTE
COMPRESS
DEMOTE

For example:

activation A:
  size          2 MB
  recompute     200 µs
  SSD reload    700 µs

→ discard

versus:

expert weights:
  size          40 MB
  recompute     impossible
  SSD reload    3 ms

→ store/cache

This is closer to ML checkpointing than traditional paging.

DeepSpeed already makes this tradeoff at framework level through parameter/optimizer offload and activation checkpointing/offload.

The OS research question is:

What happens if these policies belong to a common resource manager?

22. One particularly promising policy: Belady is almost practical

There is a fun historical connection here.

Belady's optimal cache algorithm evicts the item whose next use lies furthest in the future.

It's normally impossible because the OS doesn't know the future.

But transformers often give you a highly deterministic future access sequence.

Therefore you can approximate—or sometimes literally implement—optimal replacement.

Dense transformer:

L3 → L4 → L5 → L6

You know exactly when L3 is next used.

Thus:

next-use-distance(object)

can be metadata.

That's an unusually clean research result to demonstrate.

Compare:

FIFO
LRU
Belady/known-next-use

on model traces.

This would fit beautifully into demo-memory first and SWTOS afterward.

23. Another interesting idea: admission control based on RAM

Conventional OSes happily start processes and then may thrash.

Example:

38. The research thesis I would use

I think the strongest formulation is approximately:

Traditional operating systems virtualize scarce compute and memory under workloads with unpredictable memory references. ML workloads invert several of those assumptions: computation is increasingly cheap relative to memory, much model state is immutable, access patterns are highly predictable, some state can be recomputed or compressed, and multiple clients can share parameter streams. An ML-oriented OS can exploit those properties by virtualizing semantic model state rather than merely virtual addresses.

That gives you a real research agenda.

Not:

The distinction I would make is not “training OS versus inference OS.” It is deeper:

The historical analogy is useful

IBM's history is particularly illuminating because several distinct abstractions evolved around different workloads.

MVS-style systems were fundamentally about efficiently operating a large shared computing installation: jobs, address spaces, datasets, devices, resource allocation, accounting, scheduling, and throughput.

VM/CMS-style systems took a different approach: give each user what appears to be an entire machine, virtualize the hardware, and let radically different environments coexist.

Then Unix/Linux emphasized processes, files, pipes, users, permissions, and composability.

Later VMware, VirtualBox, Xen, KVM, and QEMU generalized the idea that:

The operating environment itself can be a managed object.

That last observation is particularly relevant to AI.

34. And the key insight from VM history is this

Virtual memory was not valuable merely because disks could impersonate RAM.

Virtualization's deeper value was:

which machine
which RAG store
which particular tools implementation

And an ML program shouldn't necessarily need to know:

Those are implementation decisions.

That is where the word operating system becomes justified.

A revised roadmap

I would now treat this as three related projects, rather than one giant AI/ML OS:

Tiny resource monitor / virtual machine substrate, derived experimentally from SWTOS: IPC, providers, capabilities, scheduling, COW objects, snapshots, resource accounting, and emulated devices.
ML Operating Environment / ML Machine, focusing first on model objects, tensor residency, streaming, COW model snapshots, quantization variants, reproducible experiments, accelerator placement, KV management, and your SPM work.
AI Operating Environment / Agent Machine, initially on much more capable hardware, focusing on durable agent jobs, virtual context, tools as capabilities, fork/join, checkpoints, context paging, model-provider virtualization, supervision, and transactional side effects.

The nice thing is that the cheap old hardware is not an embarrassment here—it is an experimental advantage. COR24, small FPGAs, ESP32-class MCUs, old SBCs, SD/SPI flash, and old SSDs force you to make resource management visible in ways that a 256-GB workstation hides. Then the exact same abstractions can later scale upward.

The conceptual split I would carry forward is therefore:

ML OS: virtualize the model and the experiment.
AI OS: virtualize the agent and its world.

And beneath both:

A small virtual-resource monitor that virtualizes scarce state rather than assuming RAM is infinite.

That feels much more historically grounded—and much more likely to lead to genuinely novel experiments—than a single "AI/ML operating system."
