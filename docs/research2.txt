1. How is Apple Silicon actually being used?

Quite directly for the CPU, but not for the GPU.

The guest kernel is AArch64. On an M-series Mac:

MLOS AArch64 instructions
        │
        ▼
QEMU "virt" machine
        │
        ▼
HVF / Hypervisor.framework
        │
        ▼
real Apple ARM cores

So QEMU is not emulating an Intel CPU and it is not translating ARM instructions into something else.

It is virtualizing the machine around those CPUs.

The README describes this accurately: QEMU/HVF gives the AArch64 guest native execution on the real ARM cores. The kernel even observes Apple's 24 MHz architectural timer frequency through CNTFRQ_EL0; QEMU TCG instead exposes its virtual 62.5 MHz timer.

This is quite a useful distinction:

CPU execution is hardware-virtualized; peripherals are virtual hardware.

MLOS therefore sees:

ARMv8/AArch64 CPU
ARM generic timer
GICv3
PL011 UART
virtio block
virtio-mmio

It does not see:

Apple AIC
Apple NVMe controller
Apple GPU
Apple ANE
Apple's physical UARTs

That is desirable for this project because it avoids building an Apple-specific OS.

2. Is the MMU emulated or virtualized?

There are actually two different "MMUs" in this project and they should not be conflated.

The ARM CPU MMU

This one is real architectural hardware exposed through virtualization.

MLOS constructs AArch64 page tables and programs the normal ARM system registers such as TTBR*, TCR_EL1, MAIR_EL1, and SCTLR_EL1.

Under HVF, the guest ARM MMU semantics are hardware-assisted by Apple's virtualization facilities.

MLOS currently uses a very simple map:

VA 0 ------------------------+
                             |
                             | identity mapping
                             v
PA 0 ------------------------+

1 GiB block mappings

The status document says the kernel turns translation on and reads SCTLR_EL1.M back to prove it is enabled.

So:

yes, MLOS already uses a genuine ARM virtual-memory/MMU mechanism.

But it is intentionally primitive.

There is currently:

an identity map,
1 GiB mappings,
no general page mapper,
no userspace address spaces,
no per-page permissions,
effectively writable/executable RAM.

That is enough for the kernel experiments but nowhere near Linux-style virtual memory.

The "ML-MMU"

This is something completely different.

The proposed ML-MMU is an experimental accelerator/device abstraction for model-state movement, associated with your emufpga work.

That does not exist yet.

The status explicitly lists:

G8 — ML-MMU emulated: not started.

Eventually I would expect the conceptual arrangement to be:

                  ARM CPU MMU
                       │
             normal loads/stores
                       │
                       ▼
               MLOS kernel memory
                       │
                       │ ML object requests
                       ▼
                  Object manager
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
        DRAM          NVMe       ML-MMU device
                                   │
                            FPGA / emulator

The ML-MMU therefore does not replace the ARM MMU.

It is much closer to a smart DMA / memory-placement / streaming device.

Today the primary route is roughly:

        │
        ├─ build bare-metal AArch64 kernel
        │
        ├─ construct bootable ARM Image
        │
        ▼
      QEMU
   -machine virt
   -accel hvf
        │
        ▼
Hypervisor.framework
        │
        ▼
Apple Silicon ARM CPU

QEMU presents an ARM virt machine, not an emulated Mac.

That distinction is important.

You are not building:

an OS for Apple Silicon.

You are currently building:

an AArch64 OS for a standardized virtual ARM computer.

That's much more portable.

The kernel consumes a device tree supplied at boot and learns RAM, CPUs, UART, GIC, etc. from it rather than hard-coding the machine layout.

That was a good architectural choice.

6. How real is this today?

There are three levels of "real."

Level 1 — real OS mechanisms

Very real.

You have:

a bare-metal Rust kernel,
architectural MMU,
interrupts,
timer,
device tree parsing,
GIC,
UART,
virtio,
block I/O,
fault handling,
object manager,
object residency.

This is not a mocked browser simulation.

The guest actually boots and reads blocks from an actual QEMU virtio-blk device.

Level 2 — real ML resource management

Partially real.

The kernel is managing real residency pressure and real I/O.

For example, its synthetic model is:

136 objects, 144 KiB across three tiers,

and an 8 KiB arena only gets through seven of 128 tiles before refusing because eviction doesn't yet exist.

That's a legitimate demonstration of the resource-management problem.

But the model bytes aren't doing useful inference.

Level 3 — useful ML workload

Not yet.

The status page is unusually clear about this:

the synthetic transformer's tiles have no arithmetic in them.

That is okay right now.

You are testing:

storage → residency → scheduling → eviction

rather than:

matmul → softmax → sampling

Keeping those separate is sensible.

7. How practical is the project?

There are two answers.

As a general-purpose OS replacement

Not practical anytime soon.

That would require enormous amounts of conventional OS functionality that have nothing to do with your experiment:

processes,
filesystems,
networking,
mature allocators,
SMP scheduling,
security,
drivers,
userspace ABI,
debugging,
libraries.

Doing all of that would bury the research.

As an experimental ML resource-control kernel

Much more practical.

And I think the current direction is increasingly coherent.

You don't need to prove that MLOS can replace Linux.

You need to prove something more constrained:

Given the same storage, RAM, workload and compute hardware, can an ML-aware object manager make measurably better residency decisions than page-oriented mechanisms?

That's testable.

M3 is now set up properly to answer it.

13. What do the existing measurements actually tell us?

The README now reports:

Operation	HVF	TCG
model-object fault	~42 µs	~91 µs

32-resident-tile sweep	~4.9 µs	~40 µs

The most interesting number is actually the 42 µs fault, because it gives you a scale.

A 42 µs software/device-management operation is tiny compared with:

SSD page-in milliseconds in bad cases,
loading tens of MB across storage,
PCIe transfer of a large expert,
executing a substantial transformer layer.

That suggests the object abstraction itself has a reasonable chance of being cheap enough.

MLOS becomes a semantic control plane

The interesting abstraction is no longer:

"an operating system that runs an ML application."

It's closer to:

A distributed guest operating system that virtualizes model state and inference resources across heterogeneous physical resources supplied by host operating systems.

    Q4_K

    38 MiB

    SSD -> RAM          1.4 ms
