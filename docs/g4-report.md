# Gate G4: known-next-use against demand, FIFO and LRU

Status: MEASURED, 2026-09-27, saga `mlos-nextuse` step 011. Supersedes
[m3-verdict.md](m3-verdict.md) (step 006), which is kept as the record of
what was measured then, before the kernel could run any of it.

**G4 is met.** On a decode-loop trace shaped by a real 1.08-billion-
parameter checkpoint, under identical residency budgets, known-next-use
replacement does 42% to 77% fewer provider reads than the better of FIFO
and LRU in the band of budgets where any policy can differ, and moves a
third to a tenth of the bytes. On the synthetic model it does 37% to 71%
fewer. It never loses. The same policy code produces the same integers in
the simulator, in the aarch64 kernel and in the x86-64 kernel.

One thing about the gate's wording has to be said first rather than
last. [PRD.md](PRD.md) s.5.1 asks for a *recorded* layer-access trace.
Nothing here was recorded from running inference, because nothing in
this repository runs inference. The traces are *derived*: the tensor
inventory and the rotating boundary come from a real checkpoint through
emufpga's importer, and the access order follows from the transformer's
forward pass. That is the strongest provenance available without an
inference engine, and it is what the plan settled on at step 010; a
recording from a real engine remains the standard the gate names, and
is recorded below as the gap to close when MLOS hosts one.

## 1. What was compared

### The policies

All four are `mlos-policy`, `no_std` and pure. A policy sees the resident
set through `Residency` -- every resident object's `ObjectMeta` and the
current tick -- and names one victim. It is asked one victim at a time
until the object being placed fits, by the same `make_room` loop in the
simulator and in the kernel.

| policy | victim | source |
| --- | --- | --- |
| demand | none: a full arena refuses | `baselines.rs` |
| FIFO | the smallest `placed_tick` | `baselines.rs` |
| LRU | the smallest `used_tick` | `baselines.rs` |
| known-next-use | the largest `horizon * 1_000_000 / min(reload_cost, recompute_cost)`, where `horizon` is `next_use - now` for a declared position, `2^40` for an object nothing has declared a future for, and a scaled guess for a probability | `nextuse.rs` |

Ties in every policy go to the lower object id, so no answer depends on
the order residents are enumerated in (the kernel's hash-slot order and
the simulator's insertion order differ).

`next_use` is written by the kernel from a declared stream
(`ml_stream_declare`, step 007) and by the simulator from the whole
trace; both compute the position with the one function
`mlos_stream::chain`, and step 009 proved the two agree to the integer.

### The budget

A real arena, not a byte count: `mlos-arena`, the kernel's allocator,
first fit over a sorted free list with 16-byte alignment and 64 free
extents, over a buffer of exactly the stated budget. Fragmentation is
counted. One budget per row for every policy; `mlos_sim::compare` cannot
express an unequal comparison.

### The costs

Weights: reload costs 3 ms plus one nanosecond per byte (a
storage-shaped figure, `mlos-synth`'s backing tier), recompute is
impossible. KV blocks: reload 0.4 ms, recompute 2 ms. Costs feed the
next-use score and the `cost` column of `Outcome`; reads and bytes do
not depend on them.

### The traces

Three, all generated by `mlos-workload`, all round-robin over sessions
that finish at different times (so recency has something to be right
about, the fairness step 004 established).

1. **Synthetic 8x16.** `Decode::of(4, 40)`: eight layers of sixteen
   1 KiB tiles, plus a KV block per layer per token; 25,200 accesses,
   144 KiB of weights. The trace the verdict was measured on and the one
   the kernel replays.
2. **MiniCPM5-1B, decode only.** `Real::of(&shape, 4, 40,
   Context::DECODE_ONLY)`: a 24-layer Llama, 1,080,632,832 parameters at
   F16, 219 tensors of which 169 are swept per token; 2,061 MiB of
   weights, 1,678 MiB swept per token, 24 KiB of KV per token; 54,150
   accesses.
3. **MiniCPM5-1B with context.** `Real::of(&shape, 8, 40, Context {
   prefix: 2048, tokens_per_block: 16 })`: the same model, eight sessions
   each arriving with 2,048 cached tokens, the cache paged sixteen tokens
   to a block; 589,694 accesses, 389 MiB of cache at peak.

The shape comes from
`crates/mlos-workload/shapes/minicpm5-1b.names.tsv`, a copy of
`emufpga/layouts/minicpm5-1b.names.tsv`, written by `emufpga import
--sidecar-only` from a manifest that `spm-extract --manifest-only` read
off the checkpoint's safetensors headers
(`ewinregirgojr/MiniCPM5-1B-Agentic-Tooluse-Merged-FP16`, shards
`ad304762…a499a6` and `3f1dd81d…45322b`). The order file that fixed the
rotating boundary is the Llama forward pass, per layer q, k, v, o, gate,
up, down, then the untied output head; emufpga's `spm-order` refuses it
if it disagrees with the checkpoint's tensor list. No weight was read.

## 3. The shape of the curve

The advantage is not a number, it is a band, and the band sits in the
same place on all three traces: **where the budget is a large fraction
of the per-token working set.**

- **Below the band, no policy matters.** The working set does not fit,
  every token is a cycle longer than the budget, and FIFO and LRU miss
  every access -- they tie exactly, because a pure cycle cannot
  distinguish them. Next-use keeps whatever fraction of the sweep fits
  and wins by that fraction: 2% of a 1,678 MiB sweep at 512 MiB, 25% at
  1,664 MiB. Bytes moved fall faster than reads because it keeps the
  large tensors and re-reads the small ones.
- **In the band, LRU beats FIFO and next-use beats LRU.** Recency starts
  to mean something once part of the working set survives a token: on
  the real shape with context LRU does 512,427 reads to FIFO's 521,669
  at 1,792 MiB, and next-use 301,800. Where the baselines differ from
  each other is exactly where the fairness argument of step 004 holds,
  and it is where the gift is worth the most.
- **Above the band, everything converges.** The budget where LRU catches
  up is the budget where the working set fits and nothing is evicted:
  256 KiB on the synthetic model, 1,792 MiB for the real shape without
  context, 2,176 MiB with it. That number is a finding in itself: for
  this model at F16 it is 87% and 106% of the weights.

The width of the band is the second finding, and it cuts against the
thesis in a way the synthetic model could not show. MiniCPM5-1B has two
KV heads, so one token's cache is 24 KiB against 1,678 MiB of weights
swept to produce it. Without context, the cache is a rounding error and
the whole problem is a weight sweep -- the degenerate case the M3 plan
warned against constructing, arriving from a real model. **Whether a
deployment is in the band is a property of the model and the serving
regime, not of the policy.** A GQA model at short context gains little
from any residency policy; a model with a large cache, or a long-context
serving regime, is where the 42% to 77% lives.

## 4. PRD Q1 and Q2

### Q1. Is the object granularity a weight tile or a whole tensor?

> Tiles give better residency control and a larger table. Start with
> tensor-granular objects and a tile sub-index; revisit after G4.

**Tensor-granular for weights; paged for KV; and the workload that would
decide it has not been run.** The step 006 measurement stands, priced
identically for both: at 128 KiB, tiles moved 29% fewer bytes and
tensors cost 6% less time, because a 3 ms seek dwarfs a 16 KiB transfer.
Step 010 adds two facts. The real shape ran tensor-granular -- 219
objects for a billion parameters -- and lost nothing to it, because a
dense sweep reads every byte of a tensor it touches. And the KV cache
had to be paged: one block per token per layer is 25,000 objects at
2,048 tokens over eight sessions, and a linear victim scan over that
set costs the simulator two to seven minutes per budget; at sixteen
tokens per block the numbers above were tractable and the result was
unchanged in kind. The case tiles exist for -- partial access, as in
expert routing or sparse attention -- is still not in any workload
here. Revisit at M5, as step 006 said.

### Q2. Does the model object table belong in the kernel or in a service?

> Provisional answer: table in kernel, *policy* in a service, with the
> policy consulted on eviction and prefetch only.

**Table in kernel: confirmed. Policy: in the kernel too, as built, and
the numbers say a service would be affordable.** In the band, hits are
the overwhelming majority of accesses: 95% at 2,048 MiB on the real
shape with context (29,639 reads of 589,694), 86% at 192 KiB on the
synthetic model. A hit is a table lookup, and if it crossed an IPC
boundary it would dominate everything. Evictions are the remaining 5%
to 14%, each behind a fault the kernel measures at about 42 us under
HVF; a few microseconds of service round trip on each would add roughly
a tenth to the fault's cost. Step 009 linked `mlos-policy` into the
kernel directly -- the crate is `no_std`, pure, and holds no state the
table does not own, so the same code runs in the simulator -- which is
the arrangement that made "identical to the integer" checkable. Moving
it behind a service later costs the round trip and nothing else.

## 5. What this does not show

1. **The traces are derived, not recorded.** Said above; repeated here
   because it is the gap between what was measured and what the gate's
   sentence asks for. A recording from a real inference engine, with
   MLOS as the residency layer under it, is what closes it, and that is
   M4 or later work.
2. **Costs are modelled.** Three milliseconds and a gigabyte a second
   are storage-shaped figures, not measurements of a device. Reads and
   bytes do not depend on them; the next-use score's cost term does.
3. **The real shape ran in the simulator only.** The kernel replays the
   synthetic trace and matches the simulator to the integer, on both
   architectures; the guest's static trace buffers are sized for that
   trace, and the real shape's weights are two gigabytes against a
   32 KiB arena. The chain of evidence is: simulator equals kernel on
   the synthetic trace, therefore the simulator's numbers on the real
   shape describe what the kernel would do with the same memory.
4. **One model.** MiniCPM5-1B is a small Llama with aggressive
   grouped-query attention. A model with more KV heads, or an MoE with
   partially-read experts, would sit differently in the band, and the
   plan's next steps should measure one.
5. **This is not evidence that MLOS beats Linux.** It is evidence that a
   policy told when objects are next wanted beats policies that guess,
   under identical budgets, on a workload shaped like inference over a
   real model's tensors -- and that a kernel can be told, cheaply
   enough, through a declared stream.

## 6. Reproduce it

```sh
# The three tables above, as markdown, with timings (about 12 minutes).
cargo test -p mlos-workload --test g4 -- --ignored --nocapture --test-threads=1

# The step-006 tables and the granularity comparison behind Q1.
cargo test -p mlos-workload --test verdict -- --ignored --nocapture --test-threads=1

# The kernel and the simulator, same trace, same budget, same integers:
# aarch64 under QEMU/TCG, then both architectures side by side.
cargo test -p mlos-cli --test replay -- --ignored
cargo test -p mlos-cli --test replay_x86 -- --ignored

# The shape, from the checkpoint's headers, in emufpga:
spm-extract --manifest-only model-00001-of-00002.safetensors model-00002-of-00002.safetensors out/
emufpga import --input out/ --output minicpm5-1b.spm --order layouts/minicpm5-1b.order --sidecar-only
```

Every number in this document was produced by the first command on
2026-09-27 at commit `ef9ef99` and pasted, not typed.

## 7. What changes in the plan

G4 is met, so M4 (`mlos-parameter-major`, gate G5) is worth doing, and
saga `mlos-two-hosts` runs first or alongside it as planned. Two
findings feed forward:

- **The band.** Whatever M4 and M5 measure should be measured at budgets
  stated as a fraction of the per-token working set, and the report
  should say where the band is for the model in hand. A single budget
  row is not a result.
- **KV granularity.** Paged KV blocks are now a `Context` parameter of
  the real workload. M4's sharing and M5's degradation ladder both act on
  KV; they should inherit the paging rather than one block per token.
