# MLOS as a layout producer -- what we provide, what we need

Status: HANDOFF. Written for the agents working in `sw-mlpl`,
`demo-extensions` and `sw-tos`. If you are looking for what MLOS is, read
[PRD.md](PRD.md); this file is only about the shared visualization.

The contract is sw-mlpl's
([`../../sw-mlpl/docs/storage-layout-viz.md`](../../sw-mlpl/docs/storage-layout-viz.md)).
MLOS adopts it unchanged. Everything below is either an artifact you can
pin, a list you need in order to render us, or a question only you can
answer.

## 2. To sw-mlpl: the vocabulary, as closed sets

`u:default_palette()` is strict -- `select_rows` errors on a kind it does
not have a row for -- so **MLOS will not render today**. Three rows are
missing. That is the whole blocker, and it is small.

### Add now (in the committed samples)

```
reserved      memory the loader owns below the kernel image
rodata        the kernel's read-only data
weight-tile   one tile of a dense layer's weights
```

`reserved` and `rodata` are not MLOS-specific; any OS memory map wants
them. `weight-tile` is the first of the ML object classes.

### Add when you want the rest of the classes

MLOS registers only weight tiles and activations today, so only
`weight-tile` appears. The ABI's class set is closed and will not grow
without a note here:

```
weight-tile  scale  expert  kv-block  activation  embed-block  rag-block  adapter
```

These are what an ML object store holds where a flash image holds
programs. `expert` and `kv-block` are the two worth having distinct
colours for: an MoE expert is selected probabilistically and a KV block
grows with a session, and those behave differently on screen.

### Already covered by your palette

`text`, `data`, `bss`, `stack`, `padding`, `free` -- used verbatim,
deliberately, so MLOS's whole `sysram` space renders with no change on
your side. We do not emit `header`, `catalog`, `image`, `state` or
`kernel`; those are SWTOS's.

### The other columns, as closed sets

| Column | Values | Notes |
| --- | --- | --- |
| `region_space` | `disk`, `dram`, `sysram` | `sysram` is in the static document only |
| `region_owner` | `kernel`, `model N`, `""` | Models, not programs. Sessions when M4 lands |
| `region_state` | `resident`, `evicted`, `never`, `fixed` | `fixed` = not an object. `evicted` is emitted by nothing yet |
| `region_tier` | `hot`, `warm`, `cold`, `stream`, `archive`, `""` | The Location mode |
| `region_next_use` | `never`, `distance N`, `probability P`, `""` | Three shapes, not a number |

Empty string means "does not apply to this region" -- a kernel section has
no tier. Group on it as a bucket, do not treat it as a colour.

`region_next_use` is a string with three *shapes* on purpose, and this is
the one place I would ask you not to simplify. A dense layer sweep yields
an exact distance; an MoE router yields a distribution. They differ in
kind, not degree: a policy may act on a distance with certainty and on a
probability only as a hint. Collapsing them into one number would licence
a viewer to draw them the same way. Today every value is `never`, because
nothing writes the field until M3 -- so a next-use colour mode would show
one colour, and is not worth building yet.

### Padding

Emitted as its own kind, distinct from `free`, exactly as SWTOS does. The
gap between two kernel sections is alignment cost and the gap at the end
is headroom; folding them together hides the first, which is usually the
number a memory map is being read to find.

### Two things that may surprise a consumer written against SWTOS

- **Empty `rel_*` columns.** The static document has no edges: nothing is
  resident in a build artifact, so there is nothing for an edge to run to.
  The columns are emitted as empty arrays rather than omitted. Please
  confirm `parse_json` is happy with `[]` -- it is the one shape I could
  not test against your interpreter from here.
- **A space with one region.** Before anything runs, the `dram` space is a
  single `free` region covering the whole arena. It tiles, it is valid,
  and it draws as one box.

## 3. To demo-extensions: what this data wants that a storage map does not

Two questions, both yours to answer. I am not assuming the primitives
already cover these.

**Two spaces side by side, with edges between them.** The picture MLOS is
for is a stored tile on the left and the arena region holding its bytes on
the right, joined. The runtime document carries 32 `backs` edges as
`rel_kind`/`rel_from`/`rel_to` over `region_id`. Does `set_boxes` plus
`set_highlight` express "draw these two spaces apart and these lines
between them", or does that want a primitive of its own?

**A time axis.** `runtime-events.jsonl` is a stream of residency
transitions. Animating it is the thing that makes an ML object store look
different from a flash image -- weights arriving, being re-used, and being
refused when the arena fills. Nothing in the proposed surface obviously
drives an animation; that may be right for now.

**One thing MLOS gets wrong for you today, and I should say so.** The
`sysram` space is 512 MiB of which ~509 MiB is one free region, against a
115 KiB `.text`. Rendered linearly the kernel is a hairline. Per-space
block sizes take the worst cross-space ratio from 16384:1 down to 512:1,
but within `sysram` this needs a log scale or an elided free tail on your
side. SWTOS does not hit it -- its flash is mostly used.

## 4. The event stream

One JSON object per line, behind an `@ev ` marker on the console; the
marker is stripped in the committed file. Self-delimited per line on
purpose: `mlos run --capture` kills the guest after a fixed number of
seconds, so a truncated capture is the normal case, and a single JSON
array would yield nothing at all without its closing bracket.

```json
{"seq":1,"event":"placed","region":553648128,"object":"72058693549555712",
 "offset":0,"bytes":1024,"cost":3001024,"tier":"cold","why":""}
```

Every key is present on every line, including the ones that do not apply.

| Key | Meaning |
| --- | --- |
| `seq` | Monotonic. The ordering a replay depends on |
| `event` | `placed`, `hit`, `refused`, `evicted` (nothing emits `evicted` yet), `dropped` |
| `region` | The `dram` `region_id`. The same object's `disk` id is `region & 0x0fffffff \| (1 << 28)` |
| `object` | The raw `ObjectId`, matching `region_object_id`. A string: it does not fit a JSON number safely |
| `offset` | Arena-relative, matching `region_start`. Not an absolute address |
| `bytes` | Zero when nothing moved |
| `cost` | Nanoseconds, as the provider charges it |
| `why` | `no-budget` and friends, for `refused` |

**There is no timestamp, deliberately.** The only clock the shell had when
this was designed is a 2 Hz tick, which cannot resolve a fault, and
elapsed time under TCG is not the timing of any real machine. Ordering is
`seq`, which is exact. Duration is `cost`, the modelled figure a provider
charges -- which is also the axis M3's policy comparison is measured on,
so it is the right one rather than a fallback.

The last line is always a `dropped` count, emitted even when zero. The
ring holds 256 events and drops the oldest; a replay over a stream with a
hole in it would rebuild the wrong picture and otherwise have no way to
know.

A `refused` event names a region that is in no space -- the object never
became resident, so it has no arena region. Its id is still the stable
name of where it would have gone, and the same object's `disk` region does
exist. Resolve against either.

## 5. To sw-tos: what MLOS did differently, and why

Same contract, four decisions taken differently. None of them is a
criticism; they are places where a second producer found the format had
more than one reasonable reading.

1. **Extra columns rather than a second document.** `region_tier`,
   `region_object_id`, `region_state`, `region_next_use`, `region_reuse`
   and `region_cost` ride in the same file. What an ML object store knows
   that a flash image does not shows up as columns, which is the argument
   for sharing a format at all.
2. **The id scheme is derived, not positional.**
   `space << 28 | class << 24 | layer << 16 | tensor << 8 | tile`, 31
   bits. The model field is deliberately absent and the derivation
   *refuses* rather than truncating when a second model appears -- a loud
   failure beats two models drawn on top of each other. If you ever need
   ids stable across two documents, this is the shape that does it.
3. **Two documents that join.** The static one says what exists, the
   runtime one says what is resident, and 128 ids appear in both naming
   the same things. That is what makes "show the model, highlight what is
   in memory" a join rather than a re-render.
4. **The validator reads the text, not the types.** Our two emitters share
   no rendering code -- one builds `Vec`s on the host, the other streams
   from a kernel with no allocator -- so the only thing that can check they
   agree is the bytes. `mlos_layout::validate(&str)` is mutation-checked
   against a dropped column, a one-region gap, an overlap, a stretched
   capacity, a reused id and a dangling edge. It is not MLOS-specific and
   you are welcome to it.

One question back: you emit `space_used` and `program_*` columns that are
not in the pinned contract. Should those be promoted, or stay producer
extensions like ours? A consumer cannot tell the difference today.

## 6. What a picture drawn from this data does and does not show

Anyone shown a rendering should be able to tell which of these they are
looking at.

**Real.** The disk image and where every tile sits in it. The kernel's
`.text`/`.rodata`/`.data`/`.bss` extents, read back from the linked ELF.
The arena's capacity and what is in it. Which tiles are resident, how many
times each has been wanted, what each cost to fetch, and the moment the
arena ran out.

**Synthetic.** The model. Eight layers of sixteen tiles with no arithmetic
in them -- the access pattern and the residency pressure are the subject,
and a demonstration of an ML operating system needs no neural network in
it. The tier costs are NVMe-shaped figures, not measurements.

**Absent.** Eviction, so no `evicted` event and no victim: the arena fills
and MLOS refuses, which is the honest outcome until M3 has a policy.
Next-use, so the column is there and always `never`. Sessions, sharing,
degradation, any GPU. `sysram` in the runtime document, because a running
kernel has no symbol table and cannot say where its own `.text` ended.

The short version: **a runtime document is a picture of a real system
managing a synthetic model, and a static document is a picture of a build.**
